# Codex Partner 目标保存失败修复（2026-10-20）

## 故障

网页保存 Goal 时会间歇性返回 500。服务日志中与保存路径共用数据库的读取先报错：

```text
sqlite3.OperationalError: disk I/O error
  File "/root/Codex-Partner/app.py", line 4515, in task_or_404
```

`PRAGMA integrity_check` 指向 `dashboard.sqlite3` 的 B-tree 页号非法：

```text
*** in database main ***
On tree page 4950571 cell 0: invalid page number 4952785
```

因此不是 Goal 业务逻辑或前端请求格式的问题，而是数据库损坏后写入失败。

## 修复

- 停止服务并保留原库：损坏快照在 `/tmp/dashboard.sqlite3.corrupt-20261020`，可读备份在 `data/dashboard.sqlite3.pre-repair-20261020`。
- 按原 schema 在临时文件逐表重建并恢复索引、触发器，随后替换为当前 `data/dashboard.sqlite3`；原损坏库和替换前库均保留。
- 重建时校验行数：tasks 6201、sessions 108436、events 3365305、task_messages 82、activity_graphs 6128、activity_nodes 66832、activity_edges 156576、activity_graph_seen 1741000；服务恢复后新产生的任务和事件正常写入。
- 新库 `integrity_check=ok`、`foreign_key_check=[]`，替换为 `data/dashboard.sqlite3` 并清理旧 `-wal`/`-shm`。
- `codex_partner/database.py` 增加启动 `PRAGMA quick_check(1)`；损坏时抛出 `DatabaseIntegrityError`，不再带病启动。
- 写入遇到 `database is locked` / `busy` 时最多重试 4 次（0、50、200、500 ms）；`disk I/O error` 等非瞬时错误立即上报，避免掩盖损坏。
- SQLite 连接超时和 `busy_timeout` 从 5 秒提高到 15 秒。
